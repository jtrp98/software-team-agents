## Status
accepted — 2026-08-24

## Context

V1 is a promise to the first users outside this repository, so it has to say exactly what is being
promised. Without one written contract, "supported" means whatever the last README edit said, and
every boundary ends up argued per incident. This ADR states the guarantees `v1.0.0` makes, each with
the mechanism (not the prose) that enforces it, plus the non-goals — the things deliberately not
promised so nobody assumes them. The release gate (`npm run release:check`, exit 0 = releasable) is
what re-proves the mechanical half of every claim below before any tag.

## Decision

**Ownership — three repos, never overlapping:**

- Framework (this repo) owns its sources: `.claude/agents/`, `contracts/`, `workflows/`, `policies/`,
  `stacks/`, hooks, plugins, orchestrator. Users amend nothing here to use the product;
  `templates/` is a build artifact regenerated byte-identically by the release gate.
- Knowledge owns project memory (`knowledge/**`, `_docs/module/**`, `decisions/**`). No agent may
  write `knowledge/_roles/**` or `.workflow/**` at all — denied to every role, tested in
  `aiBoundary.test.ts`.
- Target owns real source code. Agents write only inside preflight-resolved writable work roots
  (`AGENTCLAUDE_WRITABLE_WORK_ROOTS`); a runtime that cannot enforce a pre-tool guard is refused for
  Target-write runs (`runtimeExecutor.test.ts`).

**Runtimes — claims come from one record:** support levels are declared in
`orchestrator/src/runtime/runtimeSupport.ts`: Claude Code **Supported**, Codex **Preview**,
OpenCode **Experimental**, and levels move up only when the conformance matrix
(`runtimeConformance.test.ts`) passes and a real installation verifies it. The README table is
tested against that record word-for-word.

**OS:** Windows 10+ is the verified primary (packaged E2E runs there, including paths with spaces,
cmd/PowerShell quoting, npm shims). POSIX works and CI proves the test suite on Ubuntu, but the
Windows packaged flow is the one release-gated.

**CLI surface (stable through V1):** `sta` — `init --mode`, `configure knowledge-root|identity`,
`doctor`, `runtimes`, `run`, `status/approve/resume/retry/pause/cancel/audit`, `roles …`,
`upgrade/migrate/rollback/adopt/knowledge-migrate`, the `--check-*` gates.
`software-team-agents` — `init/sync/status/dev/ba`. Additive changes only; breaking renames are post-V1.

**Role contracts:** eleven agents (`setup`, `business-analyst`, `system-analyst`, `project-manager`,
`test-planner`, `uxui-designer`, `backend-engineer`, `frontend-engineer`, `qa-engineer`, `security`,
`devops`), each with a machine-readable contract checked against the registry by `--check-contracts`.

**Context & capability boundaries:** Least Context (role-scoped policy-filtered prompts, sliced
module docs, pointer-based retrieval — `contextSelection.ts`) and Deny by Default
(`canWritePath` denies anything no allow-list covers; universal floor > contract deny > allow list).
Prompt content is never a security boundary: contract → orchestrator → hooks/plugins enforce, and
repo/Knowledge content cannot expand a permission (`aiBoundary.test.ts`'s injection cases).

**Sync & upgrade:** plan-first sync writes nothing while a conflict stands; every overwrite/removal
is backed up first; a user-modified managed file stops sync (exit 2) instead of ever being silently
overwritten; interrupted updates converge on the next run; cross-major moves are blocked without
`--force`; `rollback` restores adoption state. Framework updates never destroy local work unannounced.

**Approval:** approvals and sign-offs are human acts recorded through `sta roles approve|signoff|ack`
— an agent cannot grant them (self-approval blocks are deterministic tests). Five points always stop
for a person: requirement interview, schema confirmation, third QA failure (or any Critical),
Critical/Important security finding, and real deploy/migration.

**State & recovery:** task state persists in SQLite (`.workflow/state.db`); runs resume, retry under
the severity-bounded escalation policy, pause, cancel, and roll back. A failed round routes back with
structured evidence, not raw history.

**V1 non-goals** (per `v1-release-improvements-TASKS.md`, unless dogfood proves a blocker): new agent
roles; new orchestration abstractions; generalized workflow DSL; analytics platform; dashboard;
distributed execution; plugin ecosystem; speculative extensibility. Also explicitly **not guaranteed
in V1**: per-module *code*-write scoping (writes are scoped to repo/workspace ownership per contract
globs; module isolation is enforced on documents and review separation) — deferred post-V1.

## Consequences

- Any change that weakens one of the mechanisms above fails the release gate rather than shipping.
- Support-level upgrades require evidence, not enthusiasm — the conformance suite plus real-install
  verification is the bar named in `runtimeSupport.ts`.
- Breaking a listed guarantee means a major version, not a patch: these words are the compatibility
  surface V1 users hold this project to.
- When V2 revises any of this, a new ADR supersedes this one rather than editing history away.
